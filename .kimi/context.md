## Occlusion-culling audit (2026-11-11)
- Scope: static audit of `engine/gpu/shadps4/video_core/renderer_vulkan/vk_occlusion.{h,cpp}`, `occlusion_model.h`, rasterizer/Liverpool integration, docs, and `engine/tests/test_occlusion.cpp`; no renderer changes requested or made.
- Design: emulate the game's ZPASS blocks with one Vulkan occlusion query per measured draw; resolve asynchronously after the GPU tick; write guest counters; skip only known hidden `SET_PREDICATION` draws. Missing, empty, incomplete, or stale measurements remain visible. Five-answer maximum history delays hiding.
- Confirmed defect: `last_dump_tick` is written by `Occlusion::Dump` on the recording thread and read by `HasUnsubmittedDumps` on the command thread without synchronization (`vk_occlusion.h:46-48,98`, `vk_occlusion.cpp:217-220`, `vk_rasterizer.cpp:3175-3176`). This is a C++ data race and can disrupt the flush needed by a query wait.
- Performance/coverage oversights: per-draw begin/end query overhead; one result-read call per closed block; 32 small guest writes per 16-DB answer; predication rejection happens only in `DrawRecord` after pipeline selection; blocks exceeding the 64-draw budget become visible; five hidden answers are required before culling; no live metrics prove net GPU/CPU savings.
- Main model has conservative fallbacks and tests for nesting, budgets, freshness, late answers, counter encoding, and predication. Tests do not cover Vulkan integration or thread synchronization.
- Verification: `/c/msys64/clang64/bin/cmake.exe --build engine/out/gpu --target occlusion-test -j 2` succeeded; `PATH=/c/msys64/clang64/bin:$PATH ./engine/out/gpu/occlusion-test.exe` printed `occlusion model: ok` and exited 0. No live GPU/visual/performance validation performed.
- Preferred direction: preserve conservative visibility; fix the race; batch query ranges/result reads where legal; carry ordered predication decisions earlier without reading live stage-B state on the decoder thread; evaluate renderer-added previous-depth/HZB bounds culling separately from game-query emulation.

## Occlusion resolution / predication deep dive (2026-11-11)
- Resolver batches inbox records per GPU tick, but calls `getQueryPoolResults` separately for every closed block (`vk_occlusion.cpp:296-348`) and may call `resetQueryPool` after every record (`:326,351-359`). Representative live sample: 19.4 answered blocks and 19.4 queries/frame, so about 19 result reads plus up to 19 reset calls/frame. Batch contiguous results and reset once after the batch; this is the clearest host optimization candidate.
- `Store` writes each counter word individually (`:361-395`): 32 `TryWriteBacking` calls for 16 DBs. It can batch a whole block with a fallback for unmapped pages. `NoteLateCommandWrite` would otherwise also lock/allocate per 8-byte word (`buffer_cache.cpp:2662-2669`), but it early-returns with write tracking; current RTX 4060 Ti log says no system-memory type for in-place game data, so do not claim that allocation cost for this capture.
- Priority resolver waits directly on `work_semaphore` (`vk_scheduler.cpp:1182-1205`), not `Scheduler::Wait`; it does not force a flush and is not included in `BbStats::tick_wait_ns`. `WAIT_REG_MEM` can drain the draw pipe and flush an unsubmitted dump (`liverpool.cpp:2016-2030`). High logged GPU-tick waits are not evidence of resolver cost. Add focused timers/counters before attributing the A/B regression.
- Per-draw query coalescing is lower priority for the sampled scene: 19.4 queries for 19.4 answered blocks means about one measured draw/block already. GPU query-command cost still needs measurement.
- Game result read is nonblocking: guest `0x216a2f0` tests all valid bits at `0x216a3ca`, sums counter deltas only when complete, and returns 10 when pending; `0xe2f190` advances the query state only on success. Polling loops are at `0xec6970`, `0xec6bf0`, `0xec6d40`. No late answers occurred live. Do not add blocking reads; guest polling is not proven to be the bottleneck.
- SET_PREDICATION is not emitted by the active game path. Game binary has valid builders `0x1077570` (enable) and `0x1077600` (disable), with callers in `0x2250690`: query object type 4 takes predication, type 3 calls ordinary query begin/end `0x2169ec0`/`0x216a070`. Live predication count and decode warnings are both zero while ZPASS activity is high. This is unused game functionality, not an observed renderer bug; optimizing it will not improve current Bloodborne gameplay.
- No code changed in that investigation. Next experiment implemented below.
